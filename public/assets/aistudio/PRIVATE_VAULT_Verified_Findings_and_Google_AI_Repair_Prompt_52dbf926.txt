N01 - CROSS-VAULT RECORD-ID COLLISIONS CAN REPLACE ANOTHER VAULT'S DATA
Priority: P0 integrity/isolation defect.
Status: SOURCE-CONFIRMED plus ISOLATED SQLITE REPRODUCTION; no Android run.

Evidence:
- data/VaultEntities.kt:76-82 makes recordId alone the global primary key;
  vaultSlot is a separate column, not part of that key.
- data/PrivateVaultDatabase.kt:40-44 inserts with OnConflictStrategy.REPLACE.
- data/PrivateVaultDatabase.kt:52-57 deletes only the selected slot, then inserts
  incoming rows whose global IDs may already belong to the other slot.
- data/VaultRepository.kt:902-939 preserves backup record IDs during restore.

Example: a record with ID X is in slot 0. Restoring a backup containing X into
slot 1 inserts X with REPLACE and replaces the slot-0 row. This breaks the promise
that a restore into one vault never touches the other. It does not show that the
decoy can decrypt the real vault; it demonstrates a cross-vault integrity risk.

The isolated SQLite check created a table with the same global-key/conflict
semantics, inserted ('same-backup-record-id', slot 0), then inserted/replaced the
same ID for slot 1. The only remaining row belonged to slot 1; slot-0 count was 0.
This confirms SQLite conflict behaviour, not a complete Android exploit test.

Repair:
- Enforce per-vault record identity at the database boundary: a composite key
  (vault_slot, record_id), or a reviewed opaque storage-ID mapping that cannot
  replace another slot's record.
- Add an explicit non-destructive Room migration preserving all existing rows
  and ciphertext/AAD compatibility. Do not change payload IDs blindly.
- Review every insert, update, lookup, delete, merge and replace for slot scoping.
- Validate incoming backup IDs and folder relationships. Remap only according to
  a documented import policy, preserving references and authenticated identity.
- Test intentionally identical IDs across both slots, not just fresh random UUIDs.

N02 - CORRUPTED RECORDS CAN BE SILENTLY OMITTED, THEN LOST
Priority: P0 data integrity defect. Status: SOURCE-CONFIRMED.

Evidence:
- data/VaultRepository.kt:982-1007 turns decryption/authentication/parsing failures
  into null through decryptEntityOrNull.
- prepareEncryptedBackupBytes:839-844 uses mapNotNull, so export can silently
  omit an unreadable record and still report success.
- merge restore:922-939 also uses mapNotNull for existing records, then replaces
  the entire target slot with the surviving/merged records. This can delete the
  unreadable original ciphertext even when the owner selected Merge.

Repair:
- Treat record-authentication/format errors as explicit integrity results.
- Abort ordinary export/merge on unexpected corruption and preserve original
  ciphertext. An optional recovery export must explicitly disclose incomplete
  data and require a separate choice; never silently call it a full backup.
- Do not rewrite/drop records that could not be authenticated.
- Test a tampered existing record, an ordinary merge and unchanged database bytes
  after rejection. Do not log decrypted record contents in diagnostics.

N03 - LATE UNLOCK COMPLETION CAN REOPEN A VAULT AFTER A LOCK EVENT
Priority: P1 session-race risk. Status: SOURCE-CONFIRMED missing guard; the race
must be reproduced deterministically in tests before claiming device impact.

Evidence:
- ui/VaultViewModel.kt:379-435 launches a password unlock job.
- lockVaultNow:438-442 cancels autosave, not the unlock job.
- data/VaultRepository.kt:291-300 opens a new session after password derivation
  without checking whether the unlock request was invalidated by screen-off,
  manual lock, a new request or another session.

Repair:
- Serialize unlock/KDF work and bind every authentication operation to a request
  generation that lock/screen-off invalidates.
- Recheck that generation at the atomic session-open boundary. Coroutine
  cancellation alone is insufficient if synchronous KDF work keeps running.
- A stale successful derivation must wipe temporary material and leave Locked.
- Test blocking the KDF, firing screen-off/manual lock, releasing the KDF and
  asserting that no new unlocked session or secret UI appears.
- Extend operation generation checks to autosave, backup preview, decoy changes
  and biometric callbacks. Serialize validation/commit where a check-then-write
  race could otherwise cross a lock boundary.

- Test a validly signed candidate whose metadata parser returns null: no

N05 - 'UPDATE DECOY PASSWORD' FLOW DELETES EXISTING DECOY RECORDS
Priority: P1 avoidable data loss. Status: SOURCE-CONFIRMED.

Evidence:
- ui/SecondaryScreens.kt:948-949 describes configuring or updating the password.
- data/VaultRepository.kt:525-577 creates a fresh decoy DEK, replaces its envelope,
  deletes all slot-1 records, then creates default/sample data.

Repair:

- A real-authorised reset that cannot preserve the decoy must explicitly warn of

  an action labelled only as changing or updating a password.

N06 - KEY/CONFIGURATION MUTATIONS ARE NOT ONE ATOMIC DATABASE OPERATION

5. DISPOSITION OF THE SUPPLIED 20-ISSUE REPORT
========================================================================

Do not blindly copy the severity labels or proposed fixes. Maintain a traceable
20-row issue checklist and record what is confirmed, changed, rejected or still
requires evidence. The following is the corrected implementation direction.

R01 - Decoy detection and database observability.
SOURCE-CONFIRMED: isDecoyModeEnabled uses decoy row count, and biometric enrollment
also uses whether decoy records exist. Deleting records must not disable the
policy for a still-valid decoy password. Store/derive an authoritative protected
configuration state, migrate it safely and test an active empty decoy. However,
adding a few fake rows or changing slot labels to HMACs does not establish
forensic invisibility. Record counts, sizes and filesystem history remain limits.
Treat the incorrect configuration/biometric policy as actionable; do not promise
that filler records make a coercion feature undetectable.

R02 - Settings exposes real/decoy differences.
SOURCE-CONFIRMED: SecondaryScreens.kt:810 conditionally hides real-only cards,
and the real settings explicitly name 'Real Vault' and 'Decoy Policy Active'.
Reduce obvious real/decoy fingerprints in normal UI. Use generic active-vault
settings, independently scoped password changes where supported, and protected
real-only management navigation. Do not copy real credentials/settings into the
decoy, show a revealing badge or create a fake biometric button that opens the
real vault. Biometrics for real unlock remain disabled while decoy is configured.
Document that UI similarity does not prove plausible deniability.

R03 - Unlock concurrency and local backoff.
SOURCE-CONFIRMED: missing in-progress guard and repository serialization allow
multiple expensive KDF requests; failure count is RAM-only. Add a single-flight
gate/Mutex and generation-aware cancellation at the repository boundary, not
just a disabled button. Persist a bounded coarse cooldown policy if desired,
address clock/reboot behaviour and explain that local delays do not prevent
offline guessing on copied ciphertext. Do not add destructive auto-wipe or a
permanent lockout. Avoid recording unnecessarily precise unlock-history data.

R04 - OTA origin and ephemeral signing.
SOURCE-CONFIRMED: URL validation restricts hosts but not the approved owner/repo;
the UI offers a custom manifest URL. Production must use the approved manifest
and release repository. Keep developer overrides in debug/test builds. Validate
normalised URL origin/path and HTTPS redirects, retaining needed asset-delivery
hosts. Keep notes as bounded untrusted plain text. Existing signer validation
reduces installation risk; do not claim a changed manifest alone can install an
attacker-signed APK. Repair release-key continuity and explicit release approval.

R05 - Immutable strings and memory lifetime.
SOURCE-CONFIRMED: UI/model/JSON flows create Strings containing secrets. Reduce
copies/lifetimes, use wipeable arrays for appropriate crypto boundaries, redact
toString/logs and clear active UI/drafts on lock. Streaming can reduce large
whole-vault copies but can still create strings/buffers. Do not promise perfect
JVM memory erasure or rewrite Compose fields into an untested homemade input
system. Managed-runtime and compromised-device limits must remain explicit.

R06 - Clipboard ownership tracking lost on restricted/null read.
SOURCE-CONFIRMED: SensitiveClipboardManager.kt:85-97 clears lastCopiedDigest
before knowing whether the clip can be inspected/cleared. Background clipboard
access is restricted on modern Android. Retain a short-lived pending clear
intent and retry when foreground/focus permits, with verified ownership and
proper expiry/cleanup. Mark secrets sensitive. Do not blindly clear any clipboard
on null or exception: it may erase a newer unrelated clip, and null is not proof
of ownership. Do not promise every OEM/version permits exact 30-second clearing
or that a clip remains forever; newer Android also has platform auto-clearing.

R07 - Unnecessary unlock telemetry persisted in plaintext preferences.
SOURCE-CONFIRMED: unlock paths save KDF benchmark results/timestamps in DataStore
(VaultViewModel.kt:392,403; AppPreferencesRepository.kt:200 onward). Stop treating
every unlock/failure as a permanent telemetry event. Keep optional diagnostics
manual/minimal and vault-safe; remove unnecessary stored exact timestamps. Keep
only non-secret update/reminder preferences and the minimum cooldown metadata
needed by the approved policy. App-private DataStore is not readable by every
ordinary third-party app; articulate the filesystem/compromised-device threat.

R08 - Password rewrapping and biometric failure handling.
MIXED: rewrapping an existing random DEK on an ordinary master-password change
is a normal key-hierarchy design, not automatically a cryptographic bug. It
does not revoke a DEK an attacker already obtained from an older compromised
copy. Explain that limitation; any explicit 'rotate encryption key after
compromise' feature needs crash-safe re-encryption and a versioned migration.
Do not force a risky full re-encryption simply because the report demands it.
SOURCE-CONFIRMED: biometric errors are swallowed in MainActivity.kt:230-278.
Handle cancellation, missing keys and invalidation visibly; retire only invalid
biometric wrappers/keys and preserve the password unlock path. Test strong
authenticator/CryptoObject configuration on supported Android versions.

R09 - Global screenshot setting can weaken another session.
SOURCE-CONFIRMED: a global preference controls FLAG_SECURE, and a decoy session
can modify that preference. Enforce a secure default for locked/setup/secret
screens. A decoy must not weaken real-vault capture policy. Any opt-out must be
deliberate, appropriately authenticated/scoped and accurately described. Never
turn it off to conceal the IME layout defect. FLAG_SECURE has platform limits.

R10 - Draft/configuration-change loss.
SOURCE-CONFIRMED: note/credential editors, setup inputs and URI selections use
remember-only state. Keep active session-scoped editor state in a lifecycle
ViewModel where appropriate, cleared on genuine lock. Preserve non-secret
operation IDs safely. Do not put plaintext passwords or note bodies into
rememberSaveable/SavedStateHandle/Bundles as a blanket fix. ViewModels survive
configuration changes, not guaranteed process death. Specify secure recovery.

R11 - Save/close flow and pending autosave.
SOURCE-CONFIRMED: NotesScreen.kt:934-936 closes immediately after requesting a
save; validation/I/O failure can leave no visible editor. VaultViewModel.saveNote
already has an onComplete(Boolean) parameter; wire it through instead of
claiming a callback must be invented from scratch. Close only after success,
or offer explicit discard while keeping the draft on failure. Back/Close must
handle pending edits/checklist text consistently. Losing the last 350 ms is a
race risk when work is cancelled/replaced/locked, not a guaranteed consequence
of every Close: the ViewModel coroutine can outlive that composable.

R12 - Folder identity and management.
