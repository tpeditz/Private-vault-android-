09. PASSWORD GENERATOR

Make the generator a first-class destination and reusable component in credential editing.

Provide:
- Password length control, with a strong useful default such as 20 characters.
- Configurable uppercase, lowercase, digits and symbols.
- An option to exclude visually ambiguous characters.
- A regenerate action.
- Show/hide and copy controls.
- An explicit "Use in credential" or "Save to Passwords" action.
- A short local explanation of the selected settings.

Use an operating-system-backed cryptographically secure random source, such as Android's appropriate SecureRandom facilities. Never use Math.random, timestamps, predictable seeds, a fixed test seed in production, sequential templates or a list of pre-generated passwords.

Use unbiased selection. If the design guarantees at least one character from every enabled category, use a reviewed unbiased construction or sampling procedure and secure shuffling; do not always put an uppercase character first and a symbol last. Explain the distribution and constraints in developer documentation.

Reject impossible settings gracefully: all categories off, length below a required category count, unsupported symbol policy or out-of-bounds lengths. Do not silently create a weaker password than the UI claims.

Do not automatically save generated values or maintain generator history. Clear temporary generated values on lock/session teardown. Saving requires a deliberate action into the currently active vault. Do not automatically copy a new password to the clipboard.

A random passphrase mode is optional only if it can be implemented locally with a bundled, licensed word list and secure uniform random word choice. It is not required to satisfy the initial scope. Do not add an online word service.

10. OFFLINE PASSWORD STRENGTH CHECKER

Provide a separate Strength Check screen and reuse its logic in credential forms.

The user can type or paste a password and receive immediate local feedback:
- A readable rating such as Very weak, Weak, Fair, Strong or Very strong.
- A concise explanation of the main weaknesses detected.
- Practical suggestions, such as use a longer unique password, avoid common phrases, remove predictable sequences or generate a fresh random password.
- A clear statement that the rating is an estimate and cannot prove safety.

Use a maintained, locally executable password-guessability estimator or a thoroughly documented conservative offline approach. Consider common-password patterns, dictionary words, keyboard walks, repetition, predictable dates and substitutions where the selected estimator supports them. Bundle required dictionaries in the app and check their licence and size.

Do not use a simplistic formula that marks every short password with uppercase, digit and symbol as strong. Do not claim precise "time to crack" values without a well-explained model; prefer qualified feedback over dramatic numerical certainty.

The checker must never send a password, password hash, hash prefix, username, service name or checker text to an API. Do not call Have I Been Pwned, a cloud AI model, analytics or a breach service. With this offline-only design, the app cannot determine whether a password appears in a current online breach database. Label this limitation accurately.

For an arbitrary input, do not save the checked password, query history or failed checker content. Use password-style input behaviour and clear it on lock. Avoid IME learning/personalised suggestions where Android supports the relevant controls; acknowledge that a compromised or untrusted keyboard is outside the app's complete control.

Local password reuse checking is scoped only to saved credentials in the current vault. Decrypt/compare only while authorised and minimise plaintext lifetime. Do not create an unencrypted global list of passwords or unsalted password hashes. No reuse warning, score, count or recommendation may reference the other vault.

Suggestions must never silently replace a stored password. If the user chooses a generated replacement, explain that they also need to update that password with the actual service before relying on the new saved value.

11. REAL ENCRYPTION AND THREAT MODEL

Design security before persisting user data. Use established cryptographic primitives and maintained libraries correctly. Never invent a cipher or describe Base64, obfuscation, string reversal, hidden filenames, a UI PIN or a plain SHA-256 digest as data encryption.

Target strong practical protection for:
- A lost or stolen locked phone.
- Copied app data and copied encrypted backup files.
- Tampered or corrupted ciphertext/backups.
- Accidental disclosure through logs, clipboard, UI previews and cache.
- Fake-password access attempting to reach real-vault data.
- A malicious, malformed or incompatible OTA update candidate.

Document limits: an unlocked compromised device, root/OS compromise, malicious keyboard, physical observation, user-selected sharing, weak chosen passwords and coercion can defeat assumptions. Do not market the application as unhackable, 100% secure or forensically invisible.

Specify the encryption boundary in writing. Sensitive data includes note titles/bodies, credential service names, account labels, usernames, emails, passwords, URLs, private notes, custom fields, folders/tags, trash contents, private timestamps and search indexes where stored. Do not encrypt only the password column while leaving sensitive metadata exposed.

Room is a persistence abstraction, not encryption. Choose a maintained encrypted database solution compatible with the actual environment, or a carefully reviewed record-encryption design over structured persistence. If using record encryption, address associated metadata, relationship leakage, indexes, WAL/journal files, temporary files, sorting and migration behaviour. State any residual metadata leakage explicitly.

Use authenticated encryption such as AES-256-GCM for appropriate record/key-wrap/backup operations, through vetted APIs. Define fresh nonce generation and uniqueness under each key, authentication-tag handling and bounded message sizes. Use domain separation and authenticated associated data where appropriate to bind ciphertext to its vault, record type, record identity and format version. Never reuse a GCM key/nonce pair or return unauthenticated plaintext after tag failure.

Use a recognised password KDF such as Argon2id from a maintained tested implementation, with fresh random salts and measured device-appropriate memory/time parameters. Do not write Argon2 yourself or set weak parameters purely for speed. Record KDF algorithm/version/parameters in the versioned envelope, bound them before allocation and test behaviour on supported lower-memory devices. Explain and review any necessary alternative before using it.

These are architecture requirements, not a complete custom cryptographic protocol. Produce a concrete key lifecycle and storage design for review, with implementation/library references, before treating this as ready for valuable secrets.

12. KEY HIERARCHY AND SECRET SEPARATION

Keep three categories distinct:
1. Vault encryption keys: protect one user's data on one installation.
2. Backup encryption keys: derived for a portable encrypted export.
3. APK release signing key: identifies official app releases for Android updates.

Never derive vault keys from the APK signing key. Never embed a universal decrypt key in the application. Each installation and each vault must have independent random data-encryption key material.

Define at least:
- Random per-vault data-encryption key generation.
- Password-derived key-encryption/wrapping keys.
- Versioned authenticated key envelopes.
- Salt and nonce creation, storage and validation.
- Unlock, lock and session termination.
- Master-password change and crash-safe rewrapping.
- Optional biometric wrapping and invalidation.
- Backup export/restore across devices.
- Migration and future key rotation.
- Failure handling for corruption, interruption and unavailable keys.

The master password must not be stored in plaintext, recoverably encrypted with a hard-coded key or sent anywhere. Use the reviewed key-unwrapping/authentication design rather than a separate quick password comparison that bypasses the intended KDF cost.

Use Android Keystore for suitable device-bound key protection. Integrate authentication with cryptographic key use when implementing biometrics; a successful biometric UI callback alone is not an adequate key-access boundary. Confirm actual hardware support rather than claiming all devices use StrongBox.

A password-wrapped portable path may still permit offline guessing if copied by an attacker. Document that protection depends on a strong master password and KDF; a biometric hardware path does not automatically strengthen every alternate path.

On master-password change, require the current real-vault authorisation and atomically update the relevant wrapping state. Preserve usable data if the process is interrupted. Do not change the decoy password, backup passwords or signing key as an accidental side effect.

Minimise decrypted data and key lifetime in memory. Clear mutable buffers where practical and release database handles/session references on lock. Do not claim perfect memory zeroisation in Kotlin/JVM or that garbage collection instantly removes every copy.

13. MASTER AUTHENTICATION, SESSION LOCKING AND RECOVERY

First use:
- Explain local storage and the importance of a strong unique master passphrase.
- Create and confirm the master password without transmitting it.
- Initialise encrypted storage and key envelopes atomically.
- Explain that there is no developer backdoor or online password reset.
- Offer decoy setup and explain its limitations privately.
- Offer biometric convenience only under the decoy-compatible policy below.

Repeated incorrect attempts must receive a generic error and a sensible local delay/backoff without revealing whether real or decoy credentials were close. Local delays are not protection against all offline attacks on copied data. Never implement automatic destructive wiping after a few failures by default.

Provide configurable auto-lock with a secure default, a manual lock action and locking on device lock. Define background behaviour and a short grace period if offered. Cover system document picker, biometric dialogs and update installer transitions explicitly; do not keep an unrestricted unlocked session indefinitely just because another activity is open.

On lock:
- Hide all secret UI immediately.
- Remove sensitive navigation/back-stack state.
- End access to the active repository/database session and key material as far as practical.
- Clear password-checker/generator transient values.
- Clear sensitive clipboard data when safe and feasible.
- Cancel or safely complete in-flight writes according to the documented transaction design.

Do not persist an "isUnlocked" preference that bypasses authentication on process restart. A fresh process must establish a new authorised session. Saved state and navigation arguments must contain identifiers only when safe, never passwords, plaintext note bodies or keys.

Forgotten master password: explain the available user-controlled backup path and its limits. An encrypted backup plus its separate backup password can support a deliberate fresh-vault restore. Do not promise recovery of an inaccessible existing vault. Never remotely reset encryption or reveal secrets to developer support.

Uninstalling, clearing app data or losing device-bound keys may destroy local access. Do not suggest uninstall/reinstall to fix a signature mismatch or migration problem when that would erase vault data.

14. FAKE VAULT / DECOY MODE - REQUIRED

Purpose: a separate fake password opens a separate ordinary-looking vault containing empty or user-created fictitious notes/credentials. This is a privacy feature for coercion scenarios, not a guarantee of personal safety or undetectable hidden storage.

Credential routing:
- Correct real master password opens only the real vault.
- Correct separately configured decoy password opens only the decoy vault.
- Every other password opens neither vault.
- An arbitrary wrong password must not automatically create/open a decoy vault.
- The real and decoy passwords must differ; validate during setup/change without exposing one from the other session.

Isolation requirements:
- Independent random data keys, password salts, authenticated key envelopes and encrypted storage contexts.
- No shared secret-bearing database connection or global singleton that retains real data in decoy mode.
- Vault-scoped repositories, caches, search, recent items, trash, favourites, settings and backup operations.
- Strongly typed or otherwise enforced session capability/active-vault identity passed through sensitive operations.
- Never decrypt the real vault merely to populate decoy UI.
- Never let an in-flight real-vault search/save/export callback update a decoy screen after session change.
- Destroy the prior session before opening a different one; cancellation and generation/session tokens should prevent stale work from crossing sessions.

The decoy interface must not show a "Decoy mode" badge, real-vault counts, hidden real folder names, real backup paths, "switch to real vault" controls or a revealing error message. Use the same general quality, navigation and update experience as the real vault. A safe internal documentation label is fine; exposing that label in ordinary decoy UI is not.

Allow the owner to prepare harmless dummy content through an authenticated real-vault configuration flow that explicitly provisions decoy data, or allow normal editing after a decoy unlock. Use fictitious credentials and reserved example domains, never working third-party credentials. If no dummy records exist, show a normal empty state.

Decoy settings must never change the real master password, real encryption state, real backup configuration or real biometric wrappers. Disabling or reconfiguring decoy mode requires a real-vault authentication context. Shared non-sensitive app settings may exist only when they cannot expose real-vault state; document them.

Biometric policy: when decoy mode is enabled, default to password entry and disable biometric unlocking of the real vault. Do not auto-launch a real-vault biometric prompt. Do not allow biometrics from a decoy session to jump into the real vault. An advanced alternative requires explicit owner choice and a reviewed design; do not silently weaken decoy behaviour for convenience.

Attempt timing/errors must not trivially identify which vault exists or which path failed. Use a reviewed approach with comparable KDF costs and generic failure handling; do not claim perfect timing indistinguishability without analysis.

Backup policy: an export contains only the currently authenticated vault. A decoy export must never include real data, real key wrappers, real counts or real-vault metadata. Do not include both vaults in one ordinary backup. Restore requires explicit authentication to its target context and must not overwrite the other vault. A fresh-install restore must bind imported data to newly created destination keys. Any design for backing up both vaults is outside this initial scope.

Limitations must be explained to the owner during setup and in private security documentation: app files, storage size, a rooted device, forensic analysis, public source descriptions or observation may reveal the presence of decoy functionality or additional data. Ordinary isolation does not provide mathematically proven plausible deniability. Never claim that the existence of the real vault cannot be detected.

Do not implement panic wiping, secret network alerts, remote commands, OS bypasses or surveillance as part of this feature.

15. BIOMETRIC CONVENIENCE WHEN DECOY IS DISABLED

Use AndroidX BiometricPrompt and supported strong authenticators where available. Tie successful authentication to authorised key use through a reviewed Keystore-backed design. Do not keep an unprotected plaintext vault key in preferences to make fingerprint unlock work.

Support no hardware, no enrolled biometric, temporary hardware errors, cancelled prompt, lockout, new enrolment, biometric key invalidation and device restart. The master-password path remains the deliberate fallback according to the documented policy. Do not reset or delete vault data when a biometric key becomes invalid.

Require appropriate authentication before enabling/disabling biometric unlock or changing sensitive security settings. Distinguish device PIN from vault master password; do not introduce a weaker device-credential fallback without an explicit design decision.

If decoy mode is later enabled, safely disable real-vault biometric convenience and remove/invalidate its applicable wrapper according to the key lifecycle. Explain the consequence to the owner at that configuration action.

16. CLIPBOARD, SCREEN, KEYBOARD AND PLATFORM PRIVACY

Use short configurable clipboard lifetime, with a proposed default around 30 seconds subject to platform behaviour. Mark copied secrets as sensitive when Android supports it. Avoid showing passwords in clipboard previews or app snackbars.

Clear only the app's still-current sensitive clipboard item where the platform allows reliable ownership/change checks; do not erase a new unrelated clip copied by the user. Handle background restrictions and OS auto-clear behaviour honestly. Do not promise that another app never read a copied value.

Block sensitive screenshots/screen recordings and recent-app previews using supported Android controls, such as FLAG_SECURE where appropriate. Apply the policy consistently to unlock, vault, generator/checker and restore-preview screens. State platform limits rather than promising absolute capture prevention.

Disable personalised keyboard suggestions where supported for secrets. Do not misuse accessibility services to control the device or block users' assistive tools unnecessarily. Never log keystrokes.

Exclude sensitive database/key/cache material from Android automatic cloud backup and device-transfer paths with the correct version-specific backup configuration. Test the actual configuration; a single manifest flag may not cover every transfer mechanism. The deliberate portable encrypted export is the supported recovery path.

Use app-private storage for internal data, narrowly scoped FileProvider access for installer handoff and Storage Access Framework for user-chosen backup files. No broad storage permission, contacts, location, SMS, microphone or camera access is needed for the core scope.

Minimise exported Android components. Validate incoming intents and URIs; never expose a deep link that bypasses vault authentication. Use no cleartext network traffic, no trust-all TLS settings and no downloaded executable plugins.

17. ENCRYPTED MANUAL BACKUP AND RESTORE

Keep this as a supporting function from the project brief, accessible from Settings or the secondary menu. It must not replace any of the four primary tools.

Export:
- Require an authenticated active-vault session and deliberate export action.
- Let the user select all supported active-vault data or Notes/Passwords sections.
- Ask for and confirm a strong dedicated backup password.
- Explain that the backup password may differ from the master password.
- Build a consistent snapshot without plaintext temporary files.
- Encrypt/authenticate it using a versioned reviewed portable format.
- Let the user choose a destination with Android's document picker.
- Report success only after a successful close/write result; show useful status and limitations of the chosen provider.

Portable format:
- Fresh random salt and nonce(s), recognised KDF and authenticated encryption.
- Explicit format version, algorithm identifiers and bounded KDF parameters.
- Only minimal non-secret header information; keep private record counts, names and detailed timestamps inside the authenticated encrypted content where practical.
- No embedded backup password, raw master password, original device Keystore key or unwrapped long-term data key.
- Document chunking/authentication order for large data if streaming is used.

Restore:
- Select a file through the system picker.
- Bound input size and untrusted header values before expensive processing.
- Request the backup password and authenticate/decrypt safely.
- Reject wrong passwords, tampering, truncation and unsupported formats without changing the current vault.
- Preview authenticated contents/counts only after successful verification.
- Offer documented merge/replace options for the current authenticated vault.
- Use staging and atomic transactions; a failure leaves current data intact.
- Resolve stable-ID conflicts explicitly; do not silently overwrite unrelated records.
- Encrypt restored records under destination-vault keys.
- Test a restore on a compatible fresh installation without the original phone's Keystore.

Do not silently write the backup to a cloud account. The system picker may let a user deliberately select a cloud-backed document provider; if they do, only the encrypted file goes there under their control. Do not add a built-in Drive integration or background upload.

Backup data may remain accessible under its old backup password after the live master password changes. Explain that changing a master password does not retroactively re-encrypt previously exported files. Do not store a plaintext backup password for unattended future exports.

18. LOCAL DATA, SEARCH AND MIGRATIONS

Use stable IDs and explicit schema versions. Model Note, Credential, Folder, Tag, their relationships, TrashRecord, vault-local settings and backup format metadata. Keep vault identity and access enforcement explicit throughout the data layer.

Validate data at UI and persistence boundaries. Use transactions for multi-record changes. Safely handle low disk space, interrupted writes, app termination, device rotation and duplicate save requests. Avoid corruption from concurrent editor/autosave and lock operations.

Keep local search confined to the active unlocked vault. Any persistent index must be protected within the encryption boundary. Do not add a global Android search provider exposing private note titles or account labels.

Production database upgrades must have tested explicit migrations. Do not enable destructive fallback migrations, silently drop tables, reset data on an exception or generate replacement encryption keys when an existing key cannot be read.

On an update, preserve real-vault data, decoy-vault data, encryption envelopes, folders, tags, favourites, trash and security preferences. Test each supported old schema. Migration failures must preserve the previous usable data and provide a clear recovery path; do not claim the update installed successfully means all vault data migrated successfully.

19. OFFLINE CONTRACT AND NETWORK BOUNDARY

The following must work in airplane mode after installation/setup: unlock, real and decoy vaults, notes, saved passwords, generator, strength checker, local reuse feedback, settings, About text and local encrypted export/restore to accessible local files.

The app itself may use the internet only to fetch the public OTA metadata and the associated APK asset. Keep the update component separate from vault data access. It must not receive database handles, master/backup passwords, note content, credential objects or encryption keys.

No analytics, ad SDKs, remote crash uploads, online licence checks, remote fonts, favicons, remote password dictionaries, Firebase services, runtime AI or hidden diagnostics. Audit transitive dependencies and packet behaviour, not merely the application's obvious network calls.

HTTPS hosting still exposes connection metadata such as IP address and request timing to the hosting service. "Offline vault" must not be described as "the app never connects to the internet" when update checking is enabled.

Provide a user setting for automatic update checks and a manual Check for Updates action. A rate-limited launch check may be the default with clear disclosure. Do not make connectivity, an update response or a mandatory login a condition for opening local data.

20. OTA ARCHITECTURE: PRIVATE SOURCE, PUBLIC UPDATES

Use two separate repositories:
- PRIVATE source repository: Android project, Kotlin/Compose source, tests, build scripts and private development documentation.
- PUBLIC OTA repository: update.json, public release notes and signed release APK assets only.

Never put source archives, private test data, vault databases, encrypted user backups, signing keystores, signing passwords, GitHub tokens or private encryption keys in the public repository. A private source repository is also not a place to commit secrets.

Public APK hosting means anyone can download that APK. Private source hosting does not make the binary private or prevent reverse engineering. The application remains local/private in its treatment of user data. If the owner later requires authorised-user-only APK distribution, stop and propose a different distribution architecture rather than embedding a shared GitHub token.

Permanent manifest address format:
https://raw.githubusercontent.com/OWNER/PUBLIC_OTA_REPOSITORY/BRANCH/update.json

Verify owner/repository/branch/file values before release. Keep the final URL in one configuration location. Do not invent a working endpoint or scatter URL strings throughout the app.

Handle first-release bootstrapping correctly. The first APK needs the permanent endpoint configured, but the final manifest's APK checksum cannot exist until that APK is built and signed. Do not create a circular dependency by embedding the APK's own checksum in itself. During development, use clearly isolated fixtures or tolerate an unavailable manifest. Build/sign/hash the APK, upload the asset, then publish the complete real manifest. Verify the live endpoint before external distribution.

The companion OTA prompt expands release execution. Both documents require the same data-preserving updater and offline contract.

21. OTA MANIFEST AND TRUST RULES

Use a documented strict JSON format. Minimum fields:
- schemaVersion: manifest format version.
- packageName: exact application ID.
- versionName: friendly display version.
- versionCode: strictly increasing release integer.
- minimumSupportedVersionCode: advisory support information for this offline product.
- downloadUrl: exact HTTPS release APK asset URL.
- sha256: actual APK SHA-256 digest.
- signingCertificateSha256: informational/consistency fingerprint, not a mutable source of trust.
- releaseNotes: bounded plain text.
- forceUpdate: false for this initial offline vault.
- publishedAt: documented ISO date/time format.

Optionally add APK byte size and minimum supported Android API to improve validation/UX. Validate their types and ranges. Reject missing security-critical fields, malformed URLs, impossible sizes, overflow values, conflicting package IDs and unsupported schema versions. Treat release notes as untrusted plain text; never render remote executable HTML.

Compare versions numerically with versionCode. Offer only a strictly greater code as this app's update policy, even if some platform install paths can accept equal version codes. Reject downgrade candidates and detect mismatches between manifest version and downloaded APK metadata.

A checksum detects corruption against the manifest; it is not sufficient authorship verification if an attacker can edit both files. Verify the candidate APK's actual signature and expected signing identity against the installed app/locally anchored trusted identity, not merely the certificate fingerprint written in the public JSON.

Use an APK signature verifier appropriate for Android, not just an API that reads an unverified certificate from a malformed archive. Android's installer must independently enforce signing/package compatibility. The first release should use one stable signer. Future key rotation requires an explicit, tested signing-lineage design; never accept a new signer just because JSON announces it.

The unsigned manifest may be used for advisory discovery only. It must never remotely disable vault access, alter encryption settings or authorise new trust roots. A signed-metadata system could be considered later if required, with separate key lifecycle and replay analysis; do not quietly add a fragile homemade signing protocol.
