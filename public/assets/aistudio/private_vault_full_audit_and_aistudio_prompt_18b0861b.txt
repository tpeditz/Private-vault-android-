1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------

1.1 Overall Security Posture and Product Quality Assessment
PRIVATE VAULT (v1.0.3, versionCode 4) is a native Android application built with Kotlin, Jetpack Compose, Material 3, Room SQLite, BouncyCastle Argon2id v1.3 (https://www.rfc-editor.org/rfc/rfc9106.html), and JCA AES-256-GCM authenticated encryption (https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html). Unlike superficial demo vaults, this codebase implements genuine cryptographic primitives:
- Two-slot unified 72-byte AES-256-GCM key envelopes (`vault_envelopes`) where both Slot 0 (Real Vault) and Slot 1 (Decoy Vault) rows always exist on disk and are sequentially derived via Argon2id on every password unlock attempt.
- Per-record AES-256-GCM authenticated encryption (`encrypted_records`) with composite primary key `(vault_slot, record_id)` and Associated Authenticated Data (`AAD = "PV1-REC|slot=$vaultSlot|id=$recordId|ver=$schemaVersion"`), leaving zero plaintext note titles, bodies, usernames, passwords, URLs, folders, or tags in SQLite columns.
- Self-contained portable `.pvault` backups (`PortableBackupEngine.kt`) with independent Argon2id key derivation, 52-byte header bound via AAD, and in-memory AEAD verification prior to database modification.
- Direct HTTPS OTA update checking (`OtaUpdateManager.kt`) verified via SHA-256 digest, official Android `com.android.apksig.ApkVerifier`, and installed signer certificate comparison.

However, a rigorous line-by-line review of all 18 Kotlin source files, Gradle configurations, CI/CD workflows (`.github/workflows/build-apk.yml` and `.github/workflows/publish-ota.yml`), and hidden repository directories (`.aistudio/`) revealed 12 Security & Cryptography Findings (`PV-SEC-001` through `PV-SEC-012`) and 14 Functional, Concurrency, UX & Completeness Bugs (`PV-BUG-001` through `PV-BUG-014`).

3. ARCHITECTURE AND DATA-FLOW MAP
--------------------------------------------------------------------------------

3.1 Core Data Flows
1. Vault Provisioning Flow (`VaultViewModel.setupNewVault` -> `VaultRepository.initializeNewVault`):
   - User enters `realPassword` (and optional `decoyPassword`) in `SetupVaultScreen.kt`.
   - `VaultViewModel` converts `String` to `CharArray` (`VaultViewModel.kt` lines 407-408) and invokes `VaultRepository.initializeNewVault` under `kdfMutex`.
   - `CryptoEngine` generates two 16-byte CSPRNG salts (`salt0`, `salt1`), two 12-byte GCM nonces (`nonce0`, `nonce1`), and two 32-byte random DEKs (`dek0`, `dek1`).
   - Argon2id v1.3 derives `kek0` from `realMasterPasswordChars` and `kek1` from either `optionalDecoyPasswordChars` or a 16-char random dummy secret (`VaultRepository.kt` lines 140-143, 177-181).
   - `CryptoEngine.wrapEnvelopePayload` packs a 56-byte inner struct (`"PVE1" | slotRoleFlag | decoyPolicyFlag | 0x0000 | createdAtEpochMs | rotatedAtEpochMs | 32B DEK`) and encrypts it with AES-256-GCM under `kek0`/`kek1` and AAD `"PV1-ENV|slot=$slotId|ver=1|alg=ARGON2ID_V13|m=...|t=...|p=..."`, yielding two 72-byte `wrappedPayloadCiphertext` blobs.
   - Starter folders and optional sample records are serialized via `VaultRecordCodec.encode` and encrypted with `dek0`/`dek1`.
   - `vaultDao.initializeVaultAtomically` writes both envelopes and initial records in one SQLite `@Transaction`.
2. Password Unlock Flow (`VaultViewModel.unlockWithPassword` -> `VaultRepository.unlockWithPassword`):
   - Checks DataStore backoff (`unlockCooldownUntilEpochMs` clamped to `MAX_COOLDOWN_MS = 30_000L`).
   - Captures `capturedAuthGen = sessionManager.currentAuthRequestGeneration()`.
   - Acquires `kdfMutex`. Loads both `slotId = 0` and `slotId = 1` envelopes from SQLite.
   - Validates KDF parameter bounds (`memoryKb in 4096..131072`, `iterations in 1..12`, `parallelism in 1..4`).
   - Sequentially runs Argon2id + AES-256-GCM unwrap on Slot 0 (`kek0`, `unwrapped0`) AND Slot 1 (`kek1`, `unwrapped1`).
   - Opens `VaultSessionManager.SessionState.Unlocked` via `openSessionIfGenerationMatches(expectedAuthGeneration, ...)` only if no lock/screen-off event occurred during KDF execution.
   - Zeroes `kek0`, `kek1`, `unwrapped0`, `unwrapped1`, and `passwordChars` in `finally` blocks.
3. Record CRUD Flow (`VaultRepository.loadDecryptedSlotSnapshotForSession` / `saveVaultItem`):
   - Every `NoteRecord`, `CredentialRecord`, and `VaultFolder` is encoded to UTF-8 JSON (`VaultRecordCodec.encode`), encrypted with AES-256-GCM using a fresh 12-byte random nonce and `AAD = "PV1-REC|slot=$vaultSlot|id=$recordId|ver=1"`, and stored in `encrypted_records` (`PRIMARY KEY(vault_slot, record_id)`).
4. Portable `.pvault` Backup & Restore Flow (`PortableBackupEngine.kt` & `VaultViewModel.kt`):
   - Export: Decrypts active slot snapshot (aborting if `hasCorruptedRecords && !allowSkipCorruptedRecords`), serializes to JSON, derives a 256-bit backup KEK via Argon2id with a fresh 16-byte salt, encrypts with AES-256-GCM (`AAD = "PV1-BACKUP|ver=1|alg=...|m=...|t=...|p=..."`), writes to `context.cacheDir/backup_staging/pending_export_<opId>.pvault`, opens a 90-second SAF picker window, copies to user-chosen `Uri` on `Dispatchers.IO`, and deletes the staging file in `finally`.
   - Restore: Reads up to 32 MiB from selected `Uri` on `Dispatchers.IO`, validates `"PVAULTB1"` header and KDF bounds, verifies AES-256-GCM tag and parses all records in memory before modifying SQLite, then commits via `replaceAllRecordsForSlot` or `upsertRecords`.
5. OTA Update Flow (`OtaUpdateManager.kt`):
   - Uses `OkHttpClient` with `followRedirects(false)` and `followSslRedirects(false)`, validating every redirect hop against `ALLOWED_HOSTS` (`raw.githubusercontent.com`, `github.com`, `objects.githubusercontent.com`, `release-assets.githubusercontent.com`), port 443, HTTPS scheme, no userinfo, and no `..` traversal before sending the next HTTP request.
   - Downloads candidate APK to `context.cacheDir/ota_updates/` only after user taps "Update Now", verifies byte size, SHA-256 digest, `com.android.apksig.ApkVerifier`, installed signer certificate SHA-256 match, and non-null `getPackageArchiveInfo` (`packageName` match and `versionCode > installedCode`).

4.1 Evaluation of Threat Scenarios
1. Lost or Stolen Device While Vault is Locked:
   - Existing Control: DEK is zeroed in memory on lock; records and envelopes are encrypted with AES-256-GCM; Keystore biometric key requires biometric authentication; Auto Backup and Device Transfer are disabled (`AndroidManifest.xml` lines 13-15, `backup_rules.xml`, `data_extraction_rules.xml`).
   - Gap / Residual Risk: Protection against offline brute-force after physical flash extraction depends on the user's Master Password entropy and Argon2id parameters (`32 MiB`, `t=3`, `p=2`).
2. Device Seized While Vault is Unlocked or Recently Unlocked:
   - Existing Control: `BroadcastReceiver(Intent.ACTION_SCREEN_OFF)` immediately locks the vault when `lockOnScreenOff == true` (`MainActivity.kt` lines 124-130); `ON_STOP`/`ON_START` lifecycle observer enforces `autoLockTimeoutMs` (`MainActivity.kt` lines 178-196); `FLAG_SECURE` blocks task-switcher snapshots and screen capture (`MainActivity.kt` lines 163-174).
   - Gap / Residual Risk: `VaultViewModel.onAppBackgrounded()` only records a timestamp and waits until `onAppForegrounded()` to call `lockNow()`! While the app is in the background, the decrypted `dekBytes` and all plaintext `notes`/`credentials` remain in RAM until the user re-opens the app or turns off the screen (`PV-SEC-007`).
3. Casual Coercion / Plausible Deniability (Attacker Demands Password):
   - Existing Control: Entering the Decoy Password unlocks Slot 1 with identical UI chrome, generic settings labels, and zero "Decoy" indicators. Both Slot 0 and Slot 1 envelopes are always 72 bytes and evaluated on every unlock.
   - Gap / Residual Risk:
     (a) If the user previously enabled Decoy Mode and later disabled it, `disableDecoyVault()` wraps Slot 1 with the hardcoded password `"xxxxxxxxxxxxxxxx"` (`PV-SEC-006`), allowing an attacker who inspects the database to prove Decoy Mode was disabled.
     (b) In raw SQLite (`encrypted_records`), `vault_slot` (`0` or `1`) is a plaintext integer column (`VaultEntities.kt` line 74). If a forensic examiner has root/ADB access to `/data/data/com.tpeditz.privatevault/databases/private_vault_encrypted.db`, they can see exact row counts in `vault_slot = 0` vs `vault_slot = 1` (accurately disclosed in `SecondaryScreens.kt` lines 1980-1981).
     (c) In `SecurityAndDecoySettingsScreen` (`SecondaryScreens.kt` line 798), if a user in the Real Vault enables Decoy Mode, `uiState.isDecoyModeEnabled` is `true` and the Biometric card displays: `"Biometric quick-unlock is disabled while multi-envelope policy is active..."`. However, when unlocked into the Decoy Vault (`slotId = 1`), `isDecoyModeEnabled` is always `false` (`VaultRepository.kt` line 93), so the Biometric card displays the `"Enable Biometrics"` button—and tapping it fails with `"Biometric settings are not available in this session."` (`VaultRepository.kt` line 385). This behavioral difference in Settings fingerprints whether the active session is Real or Decoy (`PV-SEC-008`)!
4. Malicious / Compromised OTA Update or Network MITM:
   - Existing Control: Cleartext HTTP is blocked (`network_security_config.xml`), redirects are validated hop-by-hop (`OtaUpdateManager.kt` lines 334-382), and APKs must pass SHA-256 + `apksig` + installed signer certificate match.
   - Gap / Residual Risk: Because the private key for `debug.keystore` is committed inside `.aistudio/artifacts/brain/.../debug.keystore.base64` (`PV-SEC-001`), any APK built in `debug` or `debug_compatibility` mode shares a publicly exposed private key.
5. Malicious / Curious Keyboard (IME) or Clipboard Snooping:
   - Existing Control: `SensitiveClipboardManager` marks clips with `ClipDescription.EXTRA_IS_SENSITIVE` and clears owned clips after TTL (default 30s).
   - Gap / Residual Risk: Text fields in Notes, Passwords, and Strength Audit do not disable IME personalized learning/autocorrect (`PV-SEC-004`).

5. CRYPTOGRAPHY AND KEY-MANAGEMENT DEEP REVIEW
--------------------------------------------------------------------------------

5.1 Encryption Primitive, Mode, Nonce & AAD Construction
- Algorithm & Mode: `AES/GCM/NoPadding` via standard Android/Java JCA `javax.crypto.Cipher` (`CryptoEngine.kt` lines 389, 414) with 256-bit keys (`DEK_BYTES = 32`) and 128-bit authentication tags (`GCM_TAG_BITS = 128`).
- Nonce Generation: 96-bit (`NONCE_BYTES = 12`) generated fresh on every encryption and envelope wrap via `java.security.SecureRandom` (`CryptoEngine.kt` lines 72, 145-153). Under random 96-bit nonces, the birthday bound for asingle DEK is $2^{32}$ (~4.29 billion) record writes, which is well beyond local mobile vault scale.
- Context Binding (AAD):
  - Envelopes: `"PV1-ENV|slot=$slotId|ver=$envelopeVersion|alg=${params.algorithm}|m=${params.memoryKb}|t=${params.iterations}|p=${params.parallelism}"` (`CryptoEngine.kt` line 247). Prevents moving an envelope between Slot 0 and Slot 1 or tampering with KDF cost columns in SQLite.
  - Records: `"PV1-REC|slot=$vaultSlot|id=$recordId|ver=$schemaVersion"` (`CryptoEngine.kt` line 259). Prevents copying a ciphertext from Slot 0 to Slot 1 or swapping ciphertexts between different `record_id` rows.
  - Backups: `"PV1-BACKUP|ver=$schemaVersion|alg=${params.algorithm}|m=${params.memoryKb}|t=${params.iterations}|p=${params.parallelism}"` (`CryptoEngine.kt` line 270). Authenticates the `.pvault` header fields before decryption.

5.2 Password Key Derivation (Argon2id)
- Implementation: BouncyCastle `Argon2BytesGenerator` with `Argon2Parameters.ARGON2_id` and `ARGON2_VERSION_13` (`CryptoEngine.kt` lines 171-180).
- Parameters:
  - Standard profile (`maxHeapMb >= 192`): `memoryKb = 32768` (32 MiB per slot; 64 MiB sequential across 2 slots), `iterations = 3`, `parallelism = 2`. Exceeds the OWASP Password Storage Cheat Sheet minimum baseline (19 MiB, t=2, p=1; https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).
  - Constrained profile (`maxHeapMb < 192`): `memoryKb = 16384` (16 MiB per slot), `iterations = 4`, `parallelism = 2`.
- Salt: 16 bytes (128 bits) generated via `SecureRandom` per slot and per password rotation (`CryptoEngine.kt` line 31).
- Password Byte Conversion: `charArrayToUtf8Bytes(chars)` (`CryptoEngine.kt` lines 424-433) encodes `CharBuffer` to UTF-8 and zeroes the backing `ByteBuffer` array if present. Note: Unicode normalization (such as NFC/NFKD per RFC 9106 / NIST SP 800-63B) is not applied prior to UTF-8 encoding (`PV-SEC-011`), which can cause cross-device backup restore failures if a user's password contains accented/composed Unicode characters typed on different keyboards.

FINDING ID: PV-SEC-003 (Also Tracked as PV-BUG-002)
Title:Modulo Bias and Silent Policy Downgrade in Active Password & Passphrase Generator (`OfflinePasswordStrengthEstimator`) While Unbiased `PasswordGeneratorEngine` is Unused Dead Code
Category: Cryptography / Randomness Quality
Affected Component:
- `app/src/main/java/com/example/security/OfflinePasswordStrengthEstimator.kt` (lines 250-330)
- `app/src/main/java/com/example/security/PasswordGeneratorEngine.kt` (lines 17-157)
- `app/src/main/java/com/example/ui/VaultViewModel.kt` (lines 310, 1164, 1174)
- `app/src/main/java/com/example/ui/PasswordsScreen.kt` (line 754)
Status: CONFIRMED
Severity: MEDIUM
Confidence: High
CVSS v4.0 Vector & Score: CVSS:4.0/AV:L/AC:H/AT:N/PR:N/UI:N/VC:L/VI:N/VA:N/SC:N/SI:N/SA:N (4.0 Medium)
CWE / OWASP Mapping: CWE-330 (Use of Insufficiently Random Values), OWASP MASVS-CRYPTO-1
Evidence:
1. `PasswordGeneratorEngine.kt` implements unbiased rejection sampling (`nextUnbiasedInt`, lines 142-156) and explicit `GenerationResult.InvalidConfig` when all character classes are disabled (lines 83-87). However, `PasswordGeneratorEngine` is NEVER imported or called by any file in the project!
2. Instead, `VaultViewModel.kt` and `PasswordsScreen.kt` call `OfflinePasswordStrengthEstimator.generatePassword(config)` (lines 250-299) and `generatePassphrase` (lines 304-330):
   - Line 267-270: If the user unchecks all 4 character switches (Uppercase, Lowercase, Digits, Symbols), instead of showing an error, `generatePassword` silently re-enables Lowercase and Digits (`if (pools.isEmpty()) { pools.add(filterAmbiguous(LOWER)); pools.add(filterAmbiguous(DIGITS)) }`), violating the requirement to reject impossible combinations rather than silently generating a password that contradicts the UI toggles.
   - Lines 280, 286, 292: Uses `(randomBytes[i].toInt() and 0xFF) % pool.length` and `(randomBytes[safeLength + i].toInt() and 0xFF) % (i + 1)`. Because 256 is not divisible by most pool lengths (e.g., 24, 58, 82, 88) or shuffle indices `i + 1`, this introduces classic modulo bias into every generated password and Fisher-Yates shuffle step.
   - Line 314-315: `generatePassphrase` uses `(((randomBytes[idx * 2].toInt() and 0xFF) shl 8) or (randomBytes[idx * 2 + 1].toInt() and 0xFF)) % EFF_PASSPHRASE_WORDS.size` (where `EFF_PASSPHRASE_WORDS.size` is 202, which does not divide 65,536 evenly) and line 325 uses `% 90` (which does not divide 256 evenly).
   - Furthermore, `EFF_PASSPHRASE_WORDS` only contains 202 words (~7.65 bits/word, so a 5-word passphrase has only ~38.2 bits of word entropy plus ~6.5 bits from the 2-digit number = ~44.7 bits total), yet `OfflinePasswordStrengthEstimator.evaluate()` scores a 5-word capitalized passphrase like `"Amber-Anchor-Apollo-Arctic-Arrow-42"` (~35 chars across Upper, Lower, Digits, Symbols) as `35 * log2(94) = 229 bits` of entropy ("Fortress 100/100")!
Recommended Fix:
1. Route all password generation in `VaultViewModel` and `PasswordsScreen` through `PasswordGeneratorEngine.generate()`, or replace the modulo operations in `OfflinePasswordStrengthEstimator` with `PasswordGeneratorEngine.nextUnbiasedInt()` and surface `InvalidConfig` errors in the Generator UI when all character classes are disabled.
2. In `OfflinePasswordStrengthEstimator.evaluate()`, detect passphrases composed of words from `EFF_PASSPHRASE_WORDS` (or hyphen-separated dictionary words) and calculate realistic word-list entropy (~7.65 to 11 bits per word) rather than multiplying character length by `log2(94)`.
Regression Verification:
Add a unit test verifying that disabling all 4 character classes returns a validation error and that passphrase entropy is not inflated to 200+ bits.
